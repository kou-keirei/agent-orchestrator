# AO Architecture Invariants

**Status:** Proposed normative fork doctrine  
**Date:** 2026-09-18  
**Repository:** `kou-keirei/agent-orchestrator`  
**Intended destination:** `docs/ao-architecture-invariants.md`

## Purpose

This document defines the architectural invariants that the maintained Agent Orchestrator (AO) fork must satisfy independently of any external Execution Control Plane (ECP).

AO is the execution runtime. It owns sessions, workers, worktrees, provider launches, execution-state propagation, lifecycle events, and native execution evidence.

ECP may authorize, constrain, verify, and route AO execution, but ECP must not be required to compensate for broken AO-native behavior.

> **AO must truthfully execute and report. ECP decides what that truth permits next.**

These invariants apply to manual UI launches, CLI/API launches, delegated workers, reviewers, restored sessions, resumed provider conversations, and orchestrator-managed execution.

---

## AO-I1 — Execution Truth

AO MUST preserve and expose the distinction between requested execution settings and effective runtime state.

AO-owned execution truth includes, as applicable:

- AO session identity;
- parent/orchestrator session identity;
- project/repository identity;
- worktree identity;
- exact base SHA / execution lease;
- requested and effective model;
- requested and effective effort;
- requested and effective permission / sandbox posture;
- provider identity;
- provider-native conversation/thread and turn identity;
- runtime/controller generation;
- canonical AO executable identity;
- relevant provider executable identity;
- relevant pinned toolchain identity;
- process-local environment used for validation or launch;
- lifecycle state;
- validation/conformance evidence generated by AO-native execution.

AO MUST NOT infer EFFECTIVE state merely from requested configuration.

AO MUST NOT require an implementation worker or read-only reviewer to self-attest AO-owned execution facts when AO or the provider can prove those facts directly.

### Required distinction

```text
REQUESTED
what the caller asked AO to execute

DISPATCHED
what AO actually sent to the provider/runtime

EFFECTIVE
what the provider/runtime proves actually happened
```

Authorization is external policy and belongs to ECP. AO MUST faithfully expose enough execution truth for ECP to reconcile these states.

## AO-I2 — Permission Propagation and Non-Broadening

Permission state is a first-class execution property.

AO MUST preserve permission semantics across every AO-native transition, including:

```text
manual UI selection
CLI / API creation
parent → delegated child
omitted child permission
explicit child permission
provider launch
provider-confirmed effective permission
turn configuration
resume
reconnect
restore
queued dispatch
controller handoff
Chat ↔ TUI transition
provider switch
```

### Core non-broadening invariant

In authority terms:

```text
child_effective_permission
    <=
parent_effective_permission
```

A child MAY become more restricted. A child MUST NOT become less restricted merely because a field was omitted, a default was applied, a session was restored, a provider reconnected, an interface changed, a queued turn resumed, or stale evidence was reused.

### Omitted child permission

An omitted delegated permission MUST inherit or be capped by the parent’s effective permission floor. It MUST NOT silently normalize to a broader default such as `auto`, `workspace-write`, `danger-full-access`, or provider-equivalent authority.

### Fixed read-only

For a session created with fixed preventive read-only authority:

- read-only is an immutable permission floor;
- later turns cannot broaden it;
- delegation cannot broaden it;
- reconnect/resume/restore cannot broaden it;
- unsupported provider/interface state MUST fail closed;
- unknown provider-effective permission MUST NOT be treated as proof of read-only.

### Evidence freshness

Permission evidence MUST be correlated to the current session, provider thread/conversation, provider turn where relevant, controller/runtime generation, and permission configuration generation.

A permission change invalidates stale evidence that described the previous effective state.

## AO-I3 — Model and Effort Propagation

Model and effort are first-class execution state, not cosmetic UI settings.

AO MUST correctly preserve the distinction between:

- omitted;
- explicit empty/default;
- explicit non-empty value.

Model and effort MUST propagate correctly through project/default configuration, manual UI selection, API/CLI creation, delegated child creation, Chat startup, provider startup, provider resume, persistent host restore, session restart, history/state restoration, controller handoff, and provider-native first turn.

AO MUST NOT silently replace explicit-empty semantics with omitted/default semantics when they are distinct in the provider contract.

AO MUST expose provider-native effective model/effort evidence where the provider makes it available. Where the provider does not expose a property natively, AO MUST represent that fact truthfully rather than fabricate evidence.

---

## AO-I4 — Worktree and Execution-Lease Integrity

A worker’s execution identity is bound to its authorized repository state.

An execution lease includes at minimum:

```text
project/repository identity
worktree identity
base SHA
session identity
runtime/controller generation where relevant
```

AO MUST NOT silently reuse or rebind a worker created against one base SHA as though it had been created against another.

If AO later implements explicit worker rebinding, rebinding MUST be a first-class audited operation with at least clean-worktree proof, no unaccounted unique work, previous and new lease identity, preserved/re-established permission and model/effort state, provider/runtime continuity policy, and a durable old→new lease receipt.

Dirty, ambiguous, or stale state MUST fail closed.

---

## AO-I5 — Native Lifecycle Durability

Meaningful worker state MUST survive beyond transient UI/process observation.

AO SHOULD represent meaningful worker-originated state using typed durable facts such as checkpoint, needs input, stuck, done, artifact/output reference, terminated/crashed, and worker turn settled where semantically appropriate.

AO MUST distinguish “worker became idle/settled” from “task is complete” unless the worker or a trusted AO-native mechanism explicitly establishes completion.

Lifecycle state that AO accepts as meaningful MUST not disappear merely because the daemon restarts, the UI disconnects, the parent orchestrator is idle, or the original provider controller is replaced.

---

## AO-I6 — Durable Parent Re-engagement

AO must be capable of continuing orchestration without requiring a human to act as a clock.

When a meaningful child lifecycle fact is accepted:

```text
child checkpoint/completion/failure
        ↓
durable AO lifecycle fact
        ↓
safe parent/orchestrator target resolution
        ↓
durable delivery / re-engagement
        ↓
idempotent consumption
```

The system MUST prefer at-least-once delivery with idempotent consumption over silent loss.

AO MUST prevent uncontrolled duplicate wake storms through deterministic deduplication, revision/generation identity, coalescing, bounded retry, or equivalent mechanisms.

AO MUST NOT depend on ECP for its primary native child→parent lifecycle correctness. ECP may provide an independent watchdog/fallback, but that is defense in depth.

Historical negative prior art must remain visible in implementation/review:

- repeated duplicate orchestrator re-engagement is unacceptable;
- suppressing durable completion truth merely to avoid noisy wakeups is also unacceptable.

The correct design separates “durable fact exists” from “a new provider turn must be started immediately.”

---

## AO-I7 — Canonical Runtime Identity

AO MUST be able to identify the executable/runtime it actually invokes.

Where AO manages its own CLI/hook invocation, it MUST prefer an explicit canonical executable reference over relying on mutable shell `PATH` ordering.

Relevant identity may include AO executable path/hash/version, provider executable path/version, pinned Go/Node/toolchain path/version/hash for deterministic validation, and process-local environment used for a test/build/runtime acceptance check.

A nested shell, login profile, workspace file, or ambient PATH MUST NOT silently redirect a managed AO action to an incompatible historical executable.

---

## AO-I8 — Typed Execution Outcomes

AO MUST NOT collapse materially different negative conditions into one generic `FAIL`.

AO-native result/report surfaces SHOULD distinguish at least:

```text
PASS
SOURCE_DEFECT
EVIDENCE_INCOMPLETE
ENVIRONMENT_BLOCKED
CONTROL_PLANE_BLOCKED
AUTHORITY_BLOCKED
REVIEW_PROTOCOL_FAILURE
```

Exact public names may differ, but the semantic distinction must survive transport.

- **PASS:** bounded task/review completed without a blocking issue inside its responsibility.
- **SOURCE_DEFECT:** a concrete defect exists in target source/behavior and is supported by evidence.
- **EVIDENCE_INCOMPLETE:** required proof is missing or unavailable; this is not proof of source defect.
- **ENVIRONMENT_BLOCKED:** validation could not complete because required environment/tooling/fixture state was unavailable or invalid.
- **CONTROL_PLANE_BLOCKED:** AO-native orchestration/runtime state prevented reliable execution or evidence capture.
- **AUTHORITY_BLOCKED:** the requested action requires authority absent from the execution contract.
- **REVIEW_PROTOCOL_FAILURE:** the review procedure itself was invalid or unable to reach a legitimate source verdict.

AO preserves the typed outcome truthfully. Whether that outcome authorizes repair, retry, review, escalation, or human approval is ECP policy.

## AO-I9 — Permission UX Fidelity

Supported permission modes MUST be exposed consistently across AO’s human and machine interfaces.

For preventive read-only, the manual-start UI MUST:

- expose `read-only` when the selected harness/provider supports it;
- disable or reject it before durable work when unsupported;
- send the same typed backend permission used by API/CLI execution;
- not implement a frontend-only label or shadow permission model;
- display the effective/fixed permission after launch;
- prevent later UI controls from broadening a fixed read-only session.

Canonical path:

```text
manual UI selection
        ↓
frontend typed permission
        ↓
spawn/task payload
        ↓
backend typed permission
        ↓
durable session state
        ↓
provider launch configuration
        ↓
provider-confirmed effective permission
        ↓
UI renders effective/fixed permission truthfully
```

UI state MUST NOT claim read-only merely because read-only was requested if the provider/runtime did not establish it.

---

## AO-I10 — Reviewer Evidence Semantics

Independent reviewers inspect source and evidence. They are not responsible for manufacturing AO-native execution truth from within their own inspection session.

A reviewer may verify exact target SHA, source correctness, semantic correctness, provenance/scope, supplied runtime evidence, whether that evidence actually proves the claimed behavior, and whether the review session remained non-mutating.

A reviewer MUST NOT be failed merely because its own read-only session cannot recreate provider-native model/effort/permission evidence for a different execution being reviewed.

Missing reviewer-local evidence is not automatically a source defect.

---

## Relationship to ECP

AO exposes execution primitives and truth.

ECP owns deterministic policy around those facts, including authorization, contract compilation, reviewer admission, evidence completeness policy, failure routing, repair admission, caveat inheritance, retry budgets, human-gate routing, and REQUESTED → AUTHORIZED → DISPATCHED → EFFECTIVE reconciliation.

AO MUST NOT embed ECP-specific approval policy merely to compensate for missing external control-plane logic.

ECP MUST NOT be required to repair broken AO-native propagation or lifecycle semantics.

---

## Acceptance Principle

A maintained AO build is not considered trustworthy merely because individual source patches compile.

Trust requires evidence that these invariants hold across the transitions they govern.

At minimum, pre-cutover acceptance should include:

```text
permission propagation
model/effort propagation
provider-native effective evidence
manual read-only UI path
canonical executable/runtime identity
worktree/base lease integrity
durable worker reporting
durable parent re-engagement
duplicate/retry/idempotency behavior
Windows process/argv boundary
resume/reconnect/restore behavior
```

---

## Canonical Short Form

> **AO executes truthfully. AO preserves authority floors and execution identity across transitions. AO emits durable lifecycle facts and re-engages parents safely. AO reports typed outcomes and native execution evidence. It does not ask workers or reviewers to invent control-plane truth.**
